# **Архитектурно-техническая документация: Корпоративная RAG-база знаний на Qdrant**

---

**Проект:** Enterprise Knowledge Base & Semantic Search Engine (RAG)  
**Роль разработчика:** AI Engineer / ML System Architect

**Статус:** Документация архитектуры и спецификация этапов имплементации

## **1\. Описание и назначение системы**

Данный проект представляет собой высокопроизводительную систему интеллектуального поиска и формирования ответов по внутренней документации компании (Retrieval-Augmented Generation). Система предназначена для устранения галлюцинаций языковых моделей за счет точного контекстного снабжения данных из изолированных корпоративных источников (Markdown, PDF, Notion, Confluence).

## **2\. Архитектура системы (System Architecture)**

Архитектура построена по микросервисному принципу и состоит из шести ключевых контуров: Frontend Layer (Интерфейс), Sync Agent (Синхронизация), Data Ingestion (Индексация), Retrieval Core (Гибридный поиск), Orchestration (Обработка LLM) и API Layer. Все компоненты развертываются локально в Docker-контейнерах для обеспечения полной автономности и безопасности данных.

* **Frontend Layer:** Web-интерфейс на базе Chainlit. Предоставляет чат для общения с базой знаний и отдельную вкладку "Админка" для загрузки и управления документами с указанием прав доступа (RBAC).
* **Data Ingestion & API Layer:** FastAPI-приложение, обрабатывающее как пользовательские вопросы, так и загрузку новых документов. Индексация (парсинг, чанкинг, векторизация) выполняется асинхронно через FastAPI BackgroundTasks без необходимости в отдельном watchdog-агенте.
* **Database Layer:** PostgreSQL (отдельный Docker контейнер) для хранения пользователей, ролей и метаданных загруженных файлов; Qdrant для векторного поиска.

### **2.1. Контур индексации и обработки данных (Data Ingestion Pipeline)**

* **Парсинг документов:** Преобразование разнородных форматов (PDF, Docx, MD) в единый текстовый формат с сохранением структуры заголовков.  
* **Чанкинг (Semantic / Recursive Chunking):** Разбиение документов на фрагменты размером 512–1024 токенов с перекрытием (overlap) в 10–15% для сохранения контекстных связей.  
* **Генерация эмбеддингов:** Векторизация чанков осуществляется исключительно через выделенный API-сервис в Docker-контейнере с использованием модели multilingual-e5-large.  
* **Индексация:** Сохранение векторов и метаданных в векторной базе данных Qdrant.

### **2.2. Контур гибридного поиска (Hybrid Retrieval & Reranking)**

Для достижения высокой точности контекстного поиска (Context Recall \> 90%) используется двухэтапная схема выборки:

1. **Dense Retrieval (Векторный поиск):** Выборка по евклидову расстоянию или косинусному сходству через HNSW-индекс в Qdrant.  
2. **Sparse Retrieval (Ключевой поиск):** Алгоритм BM25 для точного совпадения профессиональных терминов, артикулов и аббревиатур.  
3. **Reciprocal Rank Fusion (RRF):** Объединение результатирующих списков от BM25 и Dense поиска.  
4. **Cross-Encoder Reranking:** Переранжирование кандидатов с помощью модели bge-reranker-large для отбора Top-K (3–5 наиболее релевантных чанков).

## **5\. Жизненный цикл данных и синхронизация (Data Lifecycle)**

Загрузка и управление документами осуществляются через Frontend и API:

* **Загрузка (Upload):** Авторизованный пользователь (с нужными правами) через вкладку "Админка" в Chainlit загружает файл (PDF, Docx, MD) и указывает роли (`allowed_roles`), которым доступен этот документ.
* **Индексация (Background Task):** FastAPI сохраняет файл в Docker volume (например, `/app/data/uploads`) и запускает фоновую задачу. Задача парсит файл, бьет на чанки, генерирует эмбеддинги и отправляет их в Qdrant. В PostgreSQL создается запись о документе и его статусе.
* **Удаление:** Администратор может удалить документ через интерфейс. API удаляет файл с диска, запись из PostgreSQL и выполняет операцию `delete` в Qdrant по фильтру `doc_id`.

В Qdrant каждая коллекция конфигурируется с учетом размерности вектора и метрики расстояния:

`{`  
`"vectors": {`  
`"size": 1024,`  
`"distance": "Cosine"`  
`},`  
`"payload_schema": {`  
`"doc_id": "keyword",`  
`"department": "keyword",`  
`"created_at": "integer",`  
`"text_content": "text"`  
`}`  
`}`

## **6\. Схема баз данных и хранение метаданных**

Для обеспечения гибкого поиска и эффективной фильтрации (Pre-filtering) используется подход "Payload" в Qdrant. Данные хранятся в виде векторов с привязанными к ним структурированными метаданными.

### **6.1. Структура метаданных (Payload Schema)**

Каждый чанк (Point в терминологии Qdrant) содержит следующие обязательные поля:

* **doc\_id** (UUID): Уникальный идентификатор документа (ключ связи).  
* **filename** (String): Исходное имя файла.  
* **path** (String): Путь к файлу (относительно корня репозитория).  
* **chunk\_index** (Integer): Порядковый номер фрагмента внутри документа.  
* **metadata** (Dictionary): Объект с дополнительными атрибутами:  
  * **department** (String): Департамент, к которому относится документ.  
  * **created\_at** (Timestamp): Дата создания или индексации.  
  * **document\_type** (String): Тип документа (policy, contract, technical, etc.).  
  * **tags** (List\[String\]): Теги для кросс-категориального поиска.  
* **text\_content** (Text): Текстовое содержимое чанка.

### **6.2. Логика хранения и связей**

Хранение строится по принципу денормализации чанков: каждый чанк хранит полную информацию, необходимую для фильтрации, чтобы избежать JOIN-запросов на этапе поиска. Это обеспечивает latency \< 50ms даже при наличии миллионов чанков. При удалении документа через Sync Agent, Qdrant выполняет операцию `delete` по фильтру `doc_id`, что мгновенно очищает все чанки, принадлежащие данному файлу.

## **7\. Метрики качества и тестирование (RAG Evaluation)**

Для подтверждения промышленной надежности системы в документацию проекта включаются следующие метрики:

* **Faithfulness (Достоверность):** Отсутствие галлюцинаций, фактическая строгость ответа относительно найденного контекста.  
* **Answer Relevance (Релевантность ответа):** Соответствие сгенерированного ответа поставленному вопросу пользователя.  
* **Context Precision & Recall:** Точность работы Retrieval-модуля при выборке необходимых релевантных чанков.

## **8\. Инструкция по развертыванию (Deployment Guide)**

1. Клонировать репозиторий проекта.  
2. Развернуть инфраструктуру через Docker Compose:  
   `version: '3.8'`  
   `services:`  
     `qdrant:`  
       `image: qdrant/qdrant:v1.9.0`  
       `ports: ["6333:6333"]`  
     `web-ui:`  
       `build: ./frontend`  
       `ports: ["8051:8051"]`  
     `sync-agent:`  
       `build: ./sync`  
       `volumes: ["./docs:/app/docs"]`  
3. Запустить контейнер с сервисом генерации эмбеддингов (например, Hugging Face Text Embeddings Inference):  
   `docker run --gpus all -p 8080:80 -v $PWD/data:/data ghcr.io/huggingface/text-embeddings-inference:latest --model-id intfloat/multilingual-e5-large`  
4. Установить зависимости: pip install \-r requirements.txt  
5. Запустить сервис: uvicorn app.main:app \--reload \--port 8000

**Аппаратные требования:**

* **Для разработки:** Mac M4 (16GB RAM) — достаточен для запуска квантованных моделей.  
* **Для продакшена:** Windows PC / Linux Server (64GB RAM \+ NVIDIA GPU) — для стабильной работы под нагрузкой и высокой скорости инференса.

## **10\. Brainstorming и Принятые архитектурные решения**

1. **Отказ от Watchdog в пользу прямого API:**
   Вместо отдельного сервиса `sync-agent` с мониторингом файловой системы (watchdog), индексация выполняется через `FastAPI BackgroundTasks` сразу при загрузке файла через Admin UI. Это упрощает архитектуру (DRY), убирает race conditions при чтении ФС и дает мгновенный фидбэк о статусе загрузки. Папка `sync/` упраздняется, её логика переносится в `app/ingestion/`.

2. **Интеграция с LM Studio:**
   Генерация ответов (инференс Qwen3 4B) делегируется во внешнее приложение LM Studio. В приложении FastAPI мы будем использовать OpenAI-совместимый клиент.

3. **RBAC (Управление доступом) и БД:**
   Пользователи, их роли (admin, user, etc.) и метаданные загруженных файлов хранятся в реляционной БД (PostgreSQL в Docker контейнере). При загрузке документа к нему привязывается массив `allowed_roles`, который пишется в payload Qdrant для pre-filtering при поиске.

4. **Sparse Retrieval (BM25):**
   Нативная поддержка BM25 в Qdrant (FastEmbed sparse vectors) будет использоваться вместо in-memory индексов для масштабируемости.
